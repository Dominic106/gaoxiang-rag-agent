# 系统设计说明

## 1. 总体架构

系统分为离线建库和在线问答两条链路。

```text
源 Word 文档
  -> 文本抽取与清洗
  -> 章节元数据识别
  -> chunk 切分
  -> BM25 关键词索引 + Chroma 向量索引

用户问题
  -> 多问题拆分
  -> 问题类型识别与 query 增强
  -> 向量检索 + BM25 检索
  -> 合并、去重、重排和证据评分
  -> 证据足够：回答模型生成
  -> 证据不足：系统拒答
  -> 引用、会话和学习记忆落盘
```

## 2. 模块职责

| 模块 | 主要文件 | 职责 |
| --- | --- | --- |
| 文档处理 | `code/01_build_chunks.py` | 读取 Word、清洗文本、识别章节、切 chunk |
| 索引构建 | `code/02_build_indexes.py` | 建立 BM25 和 Chroma 向量索引 |
| 问题理解 | `code/query_understanding.py` | 识别问题类型、补充检索词 |
| 多问题拆分 | `code/question_splitter.py` | 将一条输入拆为多个独立子问题 |
| 关键词检索 | `code/rag_tokenizers.py`、BM25 | 中文分词、n-gram 和术语匹配 |
| 向量检索 | `code/doubao_embeddings.py` | 调用豆包 embedding，并缓存 query 向量 |
| 问答编排 | `code/03_query_graph.py` | 使用 LangGraph 编排完整查询流程 |
| 回答生成 | `code/deepseek_llm.py` | 在教材证据范围内生成保守回答 |
| 学习记录 | `code/study_memory.py` | 会话、上一轮、回退和长期学习画像 |
| 稳定服务接口 | `code/rag_service.py` | 为 CLI、未来 Web UI 和微信小程序提供固定的查询输入、输出、引用、错误和请求治理契约 |

### 稳定核心服务接口

`code/rag_service.py` 是当前 RAG 核心对外暴露的唯一推荐入口。调用方不需要解析 CLI 文本，也不需要直接操作 LangGraph 状态；只需要提交一个问题对象并读取固定结构的字典结果。

```python
from rag_service import query

response = query({
    "question": "什么是范围基准？",
    "session_name": "学习会话",
    "chapter": "第17章",
    "timeout_seconds": 90,
})
```

返回结构固定包含以下顶层字段：

| 字段 | 含义 |
| --- | --- |
| `schema_version` | 返回契约版本，当前为 `1.0` |
| `request_id` | 一次请求的稳定追踪编号，用于报告、会话和日志关联 |
| `status` | `ok`、`partial`、`degraded` 或 `error` |
| `answer` | 单题时的最终回答，多题时为统一汇总回答 |
| `sub_answers` | 每个子问题的独立状态、证据分、模板校验和回答 |
| `citations` | 带章节、小节、chunk_id、原文定位和片段的引用元数据 |
| `report_path` | 本次本地 Markdown 报告路径 |
| `session_turn_path` | 会话轮次文件路径，没有会话时为空 |
| `request` | 总预算、是否超时和错误类型 |
| `metrics` | 请求统计文件、总耗时和外部调用统计 |
| `error` | 稳定错误码、错误类型和用户可读消息；成功时为 `null` |

单题和多题使用同一返回结构。多题请求会先拆题、逐题检索和校验，再由系统合并回答；任何子题失败都会保留已成功子题，并通过 `partial` 或 `degraded` 明确提示调用方。

## 3. 关键设计决策

### 为什么采用 BM25 + 向量检索

向量检索擅长语义相似，BM25 擅长教材固定术语。两者合并可以兼顾“意思相近”和“术语精确命中”。

### 为什么最多三次检索

第 1 次使用增强 query 的向量 + BM25；第 2、3 次用原问题和核心关键词做 BM25 自救。这样兼顾召回率和成本，避免查不到时连续消耗 embedding API。

### 为什么证据不足时不调用回答模型

回答模型只能整理证据，不能替检索器创造证据。由系统先做证据分和核心术语覆盖检查，可以减少“看似流畅但教材没有依据”的回答。

### 为什么要保存原文来源

RAG 的可信度不仅来自答案，还来自用户能否回到章节和原始文档核对。因此每个 chunk 和每次回答都保留来源信息。

## 4. 当前数据存储

- `source_docs/`：原始 Word 文档副本。
- `indexes/chunks.jsonl`：可审计的文本块及元数据。
- `indexes/bm25_retriever.pkl`：关键词索引。
- `indexes/chroma/`：向量索引。
- `indexes/embedding_query_cache.jsonl`：查询 embedding 缓存。
- `outputs/`：回答、检索和评估报告。
- `sessions/`：会话轮次。
- `memory/`：问题历史和学习画像。

## 5. 当前边界和风险

- 当前长期记忆还没有注入下一次回答上下文。
- 当前回退只回退会话文件，不会自动重算长期画像。
- 当前评估集规模较小，不能代表所有章节的检索质量。
- 当前没有专业 reranker；逐行引用绑定和原文覆盖校验已经具备。
- 索引依赖源文档和 embedding 模型；更换模型后需要重新建向量索引。
