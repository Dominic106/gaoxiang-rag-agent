# 技术实现说明

## 1. 运行环境

- Python 项目，依赖定义在 `code/requirements.txt`。
- 编排框架：LangGraph。
- 检索和文档处理：LangChain 相关组件。
- 关键词索引：BM25。
- 向量数据库：Chroma。
- 中文切词：jieba + 中文 n-gram + 英文数字术语提取。
- embedding：豆包适配器，当前通过多模态 embedding 接口生成文本向量。
- 回答模型：DeepSeek OpenAI 兼容接口。

## 2. 运行前提

密钥只放在 `code/.env`，不写入文档、不提交到代码库、不在日志中打印。当前配置项包括豆包 embedding 和 DeepSeek 回答模型。

## 3. 建库命令

```bash
cd <项目根目录>/code
source .venv/bin/activate
python 01_build_chunks.py

```

只有在源文档、chunk 规则或 embedding 模型变化时，才需要重新建立相应索引。

## 4.1 稳定核心服务接口

未来 Web UI 或微信小程序应调用 `code/rag_service.py` 的 `query()`，不要依赖 CLI 文本输出。接口接受 `QueryRequest` 数据类或等价字典：

```python
from rag_service import query

result = query({
    "question": "定性风险分析和定量风险分析有什么区别？",
    "session_name": "软考学习",
    "timeout_seconds": 120,
})

print(result["status"])
print(result["answer"])
print(result["citations"])
```

接口契约要点：

- `question` 必须是非空字符串；`session_name`、`chapter` 和 `timeout_seconds` 都是可选字段。
- `sub_answers` 始终是列表，单题也不例外，便于客户端统一渲染。
- `citations` 统一提供 `question_index`、章节、小节、`chunk_id`、源文件和原文定位。
- `request_id` 会关联本地报告、会话轮次和 `outputs/request_metrics.jsonl`。
- `status=error` 时不会把 Python 堆栈返回给用户；详细堆栈只进入轮转日志，`error` 中只保留稳定错误码和可读消息。
- `timeout_seconds` 会覆盖本次请求的总预算，但仍受正数校验和内部剩余预算治理约束。

稳定状态含义：`ok` 表示所有子问题正常完成；`partial` 表示部分子问题完成；`degraded` 表示返回了检索到的教材证据但回答模型不可用或未通过安全校验；`error` 表示请求无法形成有效结果。

## 5. 请求超时、重试与异常日志

请求治理分成三层：

1. DeepSeek 和普通豆包 embedding 使用 OpenAI 兼容客户端的显式 `timeout` 和有限 `max_retries`。
2. 豆包多模态 HTTP 分支使用 `requests.post(..., timeout=...)`，网络异常最多按配置重试，并使用短暂指数退避。
3. LangGraph 主流程对 BM25、向量检索、回答生成、报告写入和会话写入分别降级；模型异常时只返回已检索原文，不生成未经验证的答案。

默认配置如下，可在 `code/.env` 中覆盖：

```dotenv
DEEPSEEK_TIMEOUT_SECONDS=60
DEEPSEEK_MAX_RETRIES=2
DOUBAO_TIMEOUT_SECONDS=60
DOUBAO_MAX_RETRIES=2
REQUEST_DEADLINE_SECONDS=180
CIRCUIT_FAILURE_THRESHOLD=3
CIRCUIT_RECOVERY_SECONDS=30
LOG_MAX_BYTES=5242880
LOG_BACKUP_COUNT=3
```

日志写入：

```text
<项目根目录>/logs/rag.log
```

日志采用按大小轮转，默认保留 3 个历史文件。请求日志只记录请求指纹、模型、批量大小、耗时、重试配置和异常类型，不记录 API Key 或完整提示词。发生异常时，终端显示安全提示，具体堆栈和 `request_id` 到日志中定位。

常见失败行为：

- BM25 失败：记录异常，继续尝试向量检索；如果证据仍不足，保守拒答。
- 向量库或 embedding 超时：记录异常，保留 BM25 结果；证据不足时不调用回答模型。
- DeepSeek 超时、鉴权或响应异常：记录异常，返回已检索的教材证据，不采用模型草稿。
- 报告或会话写入失败：记录异常，但尽量保留终端回答，明确提示文件没有保存成功。
- 缓存文件损坏：跳过损坏记录并记录日志，不阻断后续查询。

## 6. 关键配置

配置集中在 `code/config.py`，包括向量检索数量、BM25 检索数量、最终上下文数量、证据阈值、最大检索次数、上下文长度和回答模型输出长度。

回答模型相关配置还包括 `DEEPSEEK_TEMPERATURE=0`、`DEEPSEEK_MAX_TOKENS=1200` 和 `DEEPSEEK_THINKING=disabled`。DeepSeek V4 默认思考模式会消耗隐藏 reasoning token；本项目是低温度、强引用、固定结构的备考回答，默认关闭思考模式以把预算留给可见答案。需要研究型回答时才在 `code/.env` 中改为 `enabled`，并重新评估超时、成本和模板通过率。

调整配置时，应同步记录：调整前值、调整后值、问题现象、验证样例和成本影响。

## 5.1 全链路请求可靠性

request_governance.py 使用请求上下文把整条 CLI 查询串起来。REQUEST_DEADLINE_SECONDS 是整条查询的总预算，覆盖多问题拆分、每个子问题的检索自救、DeepSeek 首次回答、引用修复和本地报告/会话收口；外部调用会把单次 timeout 限制为“单次配置值”和“当前剩余预算”中的较小值。预算耗尽后不再发起新请求，已有教材证据仍可保留并生成诊断报告。

异常分类默认规则是：超时、连接、限流、冲突和 5xx 属于可重试；鉴权、权限、参数、响应格式和未知错误默认不可重试。豆包多模态 HTTP 分支会在每次重试前重新检查分类和总预算。DeepSeek SDK 仍保留有限 SDK 重试，但治理层会记录最终调用的稳定失败类别。

DeepSeek 和豆包各有一个进程级基础熔断器。连续可重试失败达到 CIRCUIT_FAILURE_THRESHOLD 后，短时间内直接阻断新调用；等待 CIRCUIT_RECOVERY_SECONDS 后只允许一次恢复探测。成功会清空失败计数，非重试错误不会自动触发熔断。

请求统计文件为 outputs/request_metrics.jsonl。其中输入 token 没有 provider usage 时使用“每 4 个字符约 1 token”的估算，并明确标记为 estimated；DeepSeek 返回 usage 时记录真实 prompt/completion token。该统计用于趋势、成本和故障定位，不把 API Key 或完整提示词写入磁盘。

## 9. 索引版本和健康治理

`code/01_build_chunks.py` 会先生成 manifest 骨架，`code/02_build_indexes.py` 在 BM25 和 Chroma 完成后写入最终 artifact 指纹。索引版本由教材源文件清单、chunk 元数据 schema、chunk_size、chunk_overlap、切分分隔符和 embedding provider/model 的规范化 SHA256 共同决定。API Key 不参与版本指纹，也不会写入 manifest。

`python 17_index_health.py check` 会检查源 Word 是否变化、manifest schema 是否兼容、切分参数和 embedding 配置是否漂移、chunks 是否可解析且 chunk_id 唯一、第三阶段定位字段是否完整、BM25 是否可反序列化且覆盖全部 chunk、Chroma 数量/定位元数据/目录指纹是否一致，以及构建状态是否就绪。任何一项失败都返回非零退出码。

`07_eval_retrieval.py` 和 `10_eval_hybrid_retrieval.py` 现在同时输出 JSON 汇总；`17_index_health.py compare` 兼容 JSON、CSV、Markdown，并在 Top1/Top5 下降时标记回归。最新阶段四健康报告为 `indexes/index_health_20260805_131109_499892.md`，最新指标比较报告为 `outputs/index_metric_compare_20260805_130759_931745.md`。
